# 工場切り替え高速化：ステップ別計測設計

## 1. 目的

工場切り替えの総時間を5秒未満に近づけるため、最適化に先立って処理ごとの実時間を把握する。
計測段階では、工場切り替えの処理順序・非同期化・読込対象・画面表示を変更しない。

## 2. 現状の切替フロー

`MainShellController` は、次の本処理を `runAfterUiPulse` で段階実行している。

1. 接続先・操作者の検証
2. 旧工場ワークスペースの保存
3. 新工場ワークスペースの読込
4. 環境変数とセッション断片の復元
5. 受注依頼書タブの更新
6. パイプラインチェックタブの更新
7. リモートデスクトップ・ツールバーの更新
8. 環境変数の安定化
9. 環境変数照合
10. 切替完了処理

切替完了処理の後には、表示済み状態に応じて次の後処理が続く。

1. 会社勤怠データの再読込
2. 社員勤怠データの再読込
3. 機械カレンダーの再読込
4. マスタ配台データの再読込
5. タブのバックグラウンド読込開始・完了待ち

## 3. 計測仕様

### 3.1 ログ形式

既存の `appendLog` を利用し、次の固定形式で出力する。

```text
[factory-timing] phase=<phase-name> workMs=<n> elapsedMs=<n>
```

- `phase`: 固定された処理段階名。日本語表示文言には依存しない。
- `workMs`: その段階の処理本体が実行された時間。
- `elapsedMs`: 切替開始からその段階の処理が終了するまでの経過時間。

切替完了時には既存の総時間ログを維持し、次の形式で補足する。

```text
[factory-timing] totalMs=<n>
```

後処理についても同じ形式で計測し、本処理と後処理のどちらが支配的か比較できるようにする。

### 3.2 計測境界

計測開始は、`switchActiveFactorySite` が切替コンテキストを生成した時点とする。
各本処理の境界は `executeFactorySiteSwitchWork` の各 `step` ケースの入口・出口とする。
各後処理の境界は `executeFactorySiteSwitchPostWork` の各 `unit` ケースの入口・出口とする。

`runAfterUiPulse` による待機時間と処理本体の時間を混同しないよう、少なくとも処理本体の時間を記録する。
必要な場合に待機がボトルネックか判別できるよう、切替全体の `elapsedMs` も併記する。

### 3.3 既存動作への影響

- 処理の順序、スレッド、読込条件、進捗ダイアログの制御は変更しない。
- ログ出力以外の副作用を追加しない。
- 例外時も、既存の終了処理を妨げない範囲で計測ログを残す。
- 個人情報、環境変数の値、ファイル内容はログに出力しない。

## 4. 計測結果を使った次段階

複数回の工場切り替えで、本処理と後処理の各 `workMs` および総時間を比較する。
最大の工程を一つだけ対象にし、次のいずれかを検討する。

- 現在の工場切替直後に不要な処理なら、表示時またはバックグラウンドへ遅延する。
- 独立したファイル読込なら、データ読込とJavaFX UI反映を分離する。
- 同じファイル・設定の再読込なら、既存キャッシュや差分更新を利用する。
- `workMs` が小さく待機時間が大きいなら、パルス境界や段階スケジューリングを見直す。

最適化は一度に一つだけ行い、各変更後に同じ計測で効果とデータ整合性を確認する。

## 5. 検証

### 自動検証

- 既存のJavaテストを実行し、計測追加で回帰がないことを確認する。
- 既存の工場ワークスペース復元・進捗ダイアログ関連テストが通ることを確認する。
- コンパイル警告は既存分と新規分を区別して確認する。

### 手動受入確認

異なる2工場を複数回切り替え、次を確認する。

- `[factory-timing]` が本処理・後処理の各段階に出力される。
- `totalMs` と各工程の時間関係から最大工程を特定できる。
- 切替後の工場、環境変数、表示済みタブの内容が従来と同じである。
- 操作者選択が必要な場合や切替失敗時にも、既存の復帰動作が維持される。

## 6. 対象外

この仕様では、計測結果を得る前の性能改善、処理の並列化、タブ更新の遅延化、キャッシュ仕様変更は行わない。
